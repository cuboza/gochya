## 0. ЧТО ТАКОЕ GOCHYA — в одном абзаце

**GOCHYA** — кроссплатформенная игра-виртуальный питомец. **Телефон (iOS/Android, Flutter) — полноценный самодостаточный клиент, проходимый без часов** и рассчитанный на основную аудиторию; **часы (Samsung Galaxy Watch на Wear OS, Apple Watch на watchOS) — премиум-опыт поверх**, чья ключевая эксклюзивная фича — запись ударов. Три уникальные механики формируют УТП: (1) **запись реальных ударов через акселерометр** превращает твои движения в боевые приёмы, валидируемые пульсом (**только на часах**; телефонные игроки добывают карты игрой — см. `MECHANIC_COMBAT_RECORDING.md §0`); (2) **бридинг** позволяет скрещивать питомцев с генетическим наследованием и мутациями; (3) **симбиоз** — твоя реальная активность (шаги, сон, тренировки) напрямую растит питомца. Поверх — PvP-авто-битвы (единый кроссплатформенный пул), сезонные чемпионаты, экономика снаряжения и гача.

## 2. АРХИТЕКТУРНЫЕ ПРИНЦИПЫ (НЕНАРУШИМЫЕ)

Эти правила действуют для **любой** задачи. Нарушение = баг по определению.

### 2.1. Общее ядро — source of truth
- Вся игровая логика (состояние питомца, бой, экономика, геном, мутации, vitality) реализована **только** в Shared Core.
- Клиенты (watchOS, Wear OS, Flutter) и сервер **импортируют** ядро и не дублируют формулы.
- Любая формула, написанная в клиенте/сервере напрямую → ошибка. Сначала добавить в `CORE_FORMULAS.md`, реализовать в ядре, потом вызывать.
- Ядро **детерминировано** (одинаковые входы → одинаковые выходы, без `rand()` вне `Rng` с seed).

### 2.2. Сервер — авторитет
- Бой, PvP-результаты, IAP, геном потомка, мутации, vitality **считаются на сервере**.
- Клиент только отправляет намерения («хочу дуэль», «выбираю карту X») и отображает результат.
- Клиент **никогда** не решает исход боя и не присваивает предметы/валюту.
- **Исключение (audit S2):** `technique_type` (тип удара) — доверенный клиентский ввод, так как его серверная верификация потребовала бы передачи сырого сигнала. Защита — вероятностный аудит распределения типов (`ANTICHEAT.md §3.5`), не жёсткая валидация.
- См. `docs/05-security/ANTICHEAT.md`.

### 2.3. Батарея — главный KPI носимой платформы
- Никакого фонового опроса сенсоров игрой (акселерометр/пульс включаются только в Dojo на ~16 сек).
- AOD ≤ 1 FPS, монохром.
- Все фоновые задачи — через системные API (HealthKit / Samsung Health), чтение агрегатов, не raw signal.
- Performance-бюджет см. в `CLIENT_*.md`.

### 2.4. Приватность (privacy-first, финализировано в audit S1)
- Сырые данные сенсоров (сырой сигнал акселерометра, гироскопа, raw ЭКГ/пульс) **никогда не покидают устройство**.
- На сервер уходят только производные метрики: 4 числа пульса (`HR_present/mean/delta/confidence`), нормированные дневные агрегаты, schema-versioned feature summary Dojo без временного ряда, `replay_hash`, ID карт и геном. Dojo payload привязан к server nonce, platform attestation и зарегистрированному device key (`ANTICHEAT.md §2.1, §3.3a–b`).
- **Чего НЕТ в античите:** серверной спектральной/гироскопической валидации формы удара (физически невозможна без передачи сигнала). См. `ANTICHEAT.md §3.7`.
- Явный consent на доступ к сенсорам и health-данным. Отказ → деградированный режим без блокировок.

### 2.5. Этичная монетизация и баланс
- PvP-матчмейкинг по **«эффективной силе»** (effective power), не по уровню. Платное снаряжение не даёт гарантированной победы.
- Дроп-таблицы гачи **опубликованы** в приложении.
- Без pay-to-win, без obrigatory-подписки, без рекламы на часах.

## 3. ОГРАНИЧЕНИЯ ПЛАТФОРМ — короткая шпаргалка

| Параметр | Galaxy Watch (Wear OS) | Apple Watch (watchOS) |
|---|---|---|
| Форма экрана | круглый 1.2–1.5″, ~450–480px | прямоугольный: 396×484 (45мм), 410×502 (49мм Ultra) |
| RAM | ~1.5–2 ГБ | ~1–2 ГБ (S9 ~1 ГБ, Ultra 2 ~2 ГБ) |
| Батарея | 282–590 мАч | ~308–762 мАч (максимум — Ultra 2) |
| Ввод | тач, rotating bezel, кнопка, Bixby | тах, Digital Crown, кнопка, Siri |
| Акселерометр | `SensorManager` TYPE_ACCELEROMETER | `CMMotionManager` |
| Пульс realtime | Samsung Health Sensors API (~1 Гц, **требует partner approval**) | `HKWorkoutSession` + `HKLiveWorkoutBuilder` (только так) |
| Здоровье | Samsung Health SDK, Health Services | HealthKit |
| IAP | **через companion** (Galaxy Store IAP на часах не сертифицирован) | StoreKit 2 |
| Рантайм | **нативный Kotlin + Filament + Compose for Wear OS** | **натив** SwiftUI + WatchKit + SpriteKit + Core plugin |
| AOD | AmbientModeSupport | WidgetKit / complications, 1 FPS |

> **Оба клиента нативные.** Unity на Wear OS не имеет официальной поддержки (audit S3) и заменён на нативный Kotlin + Filament. watchOS-клиент всегда был нативным (Unity не поддерживает watchOS). SceneKit deprecated (WWDC 2025) — заменён на SpriteKit для soft 3D look.

## 4. ПОРЯДОК ЧТЕНИЯ ДОКУМЕНТАЦИИ ПЕРЕД ЗАДАЧЕЙ

Перед началом **любой** задачи выполни:

1. Прочитай свой ролевой файл из таблицы в разделе 1.
2. Прочитай `docs/04-core/CORE_SPEC.md` — чтобы понимать, какие типы и функции уже есть.
3. Прочитай `docs/04-core/CORE_FORMULAS.md` — все числовые зависимости.
4. Прочитай `docs/05-security/ANTICHEAT.md` — если задача касается боя/PvP/экономики/сенсоров.
5. Прочитай связанные механики из `docs/02-mechanics/`.
6. Сверься с `docs/07-roadmap/MVP.md` — входит ли задача в MVP-скоуп.
7. Если задача меняет баланс — обнови `docs/05-security/BALANCE.md` и `CORE_FORMULAS.md`.
8. Если задача добавляет публичный API ядра — обнови `CORE_SPEC.md`.

**Правило:** документация живая. Любое изменение поведения должно отражаться в `.md`. Коммит без обновления docs = незавершённая работа.

## 5. СТАРТОВЫЕ ЗАДАЧИ (если тебя зовут «начни разработку»)

По умолчанию, если пользователь не указал конкретную задачу, работай в следующем порядке (он же — фундамент всего):

### Этап 0 — Фундамент Shared Core (обязательно первым)
1. Инициализировать монорепо: `core/` (Rust), `clients/watchos/` (Swift/SpriteKit), `clients/wearos/` (Kotlin/Filament), `clients/companion/` (Flutter), `server/` (Go+cgo), `docs/` (уже есть).
2. Реализовать типы из `CORE_SPEC.md`: `Genome`, `Pet`, `TechniqueCard`, `HeartRateEvidence`, `DailyActivitySnapshot`, `MatchResult`.
3. Реализовать формулы из `CORE_FORMULAS.md`: `quality_score`, `validate_heart`, `compute_vitality`, `simulate_combat` (включая AI выбора карт из §5.2-extended).
4. Покрыть ядро unit + property + golden тестами на детерминизм: одинаковые входы → одинаковые выходы на всех платформах.
5. CI: сборка ядра под 5 deployment-таргетов (`aarch64-apple-ios`, `arm64_32-apple-watchos`, iOS Simulator, `aarch64-linux-android`, `x86_64-unknown-linux-gnu`) плюс native test target. Точный simulator target фиксируется build-матрицей Xcode.

### Этап 1 — MVP-вертикаль (см. `docs/07-roadmap/MVP.md`)
Скоуп vertical slice: 3 разных стартовых вида (Fire / Water / Earth) с уникальными силуэтами и 1 отдельный Steam-гибрид, 4 потребности, Egg→Baby→Teen→Adult, 1 Strength-мини-игра, 3 типа ударов с heart gate на Wear OS, casual PvP, базовый бридинг, 2 активные валюты и магазин из 6 предметов. Ranked, сезоны, лиги, друзья, IAP, гача, Battle Pass и полный watchOS-клиент идут в Alpha/Beta. Точный контент — `docs/07-roadmap/CONTENT_MANIFEST.md`.

### Этап 2 — Expansion
Бридинг с рынком, гибриды, сезонные чемпионаты, кланы, Battle Pass.

## 6. ФОРМАТ ОТВЕТОВ AI-АГЕНТА

- **Сначала план, потом код.** Для любой задачи >1 файла — `EnterPlanMode` и согласуй подход.
- **Ссылайся на файлы и строки** как `docs/04-core/CORE_SPEC.md:142`.
- **Числа из формул бери из `CORE_FORMULAS.md`.** Не придумывай магические числа в коде.
- **Если спецификация неполна или противоречива** — не додумывай, задай вопрос через `AskUserQuestion`.
- **Пиши тесты.** Ядро и формулы — обязательно, клиент — по возможности.
- **Код читается как окружение:** имена, отступы, комментарии — в стиле соседних файлов.
