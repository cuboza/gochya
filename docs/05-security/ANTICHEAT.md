# АНТИЧИТ И БЕЗОПАСНОСТЬ

> Многослойная защита. Главный принцип: **сервер — авторитет**, клиент — тонкий. Подробности по механикам — в `docs/02-mechanics/`.
>
> **Архитектурное решение (аудит S1+S2):** privacy-first финализирован. Античит работает **только** на производных метриках, покидающих устройство; сырой сигнал сенсоров **никогда** не передаётся. Это физически исключает «серверную спектральную/гироскопическую валидацию» — эти слои убраны (см. §3). Вместо них: heart gate + replay-detection + клиентская энтропия + вероятностный аудит типа удара. Тип удара — доверенный клиентский ввод (см. §3.5).

---

## 1. ПРИНЦИПЫ

1. **Server-authority:** всё, что влияет на исход (бой, награды, экономика, геном, мутации, IAP) — считается на сервере.
2. **Defense in depth:** ни один сигнал не решает в одиночку — кроме жёстких отказов (§3.0).
3. **Soft on players, hard on cheaters:** лучше пропустить подозрительную запись, чем забанить честного игрока. Автоматические блокировки — только для явных ботов/эксплойтов.
4. **Logging over banning:** подозрительные события пишутся в `anticheat_events`. Action — после накопления паттерна.
5. **Privacy first:** сырые данные сенсоров не покидают устройство. Это ограничивает набор возможных проверок — см. §3.7.

### 2.1. Threat model и граница доверия

| Атакующий | Возможности | Защита | Остаточный риск |
|---|---|---|---|
| Повторяющий запросы клиент | Повтор валидного payload | server nonce, idempotency, replay cache | низкий |
| MITM | Чтение/изменение трафика | TLS, pinning как дополнительный слой, подпись payload | компрометация устройства обходит pinning |
| Модифицированный APK/app | Произвольные `metrics`, `heartEvidence`, entropy и type | Play Integrity / App Attest, attested device key, version policy | аттестация снижает риск, но не доказывает физический удар |
| Root/jailbreak + runtime hooks | Подмена sensor callbacks и памяти процесса | integrity verdict, risk score, лимиты наград, behavioral review | полностью исключить spoofing без доверенного hardware pipeline нельзя |
| Bot farm / multi-account | Массовые официальные клиенты и автоматизация | rate limits, account/device graph, economy caps | false positives требуют апелляции |

**Граница доверия:** все числовые признаки Dojo являются клиентскими утверждениями.
Heart gate подтверждает правдоподобную нагрузку только на немодифицированном клиенте;
он не является криптографическим доказательством пульса или удара. Attestation
подтверждает происхождение приложения и состояние окружения, но также не заверяет
физический смысл sensor data.

## 3. DOJО — ВАЛИДАЦИЯ ЗАПИСИ УДАРА

> ⚠️ **Переработано в аудите (S1).** Прежние §3.3 «спектральная подпись на сервере» и §3.4 «гироскопическая сигнатура на сервере» **удалены как физически невозможные**: валидация формы сигнала требует передачи самого сигнала, что нарушает privacy-first принцип. Античит сведён к трём покидающим устройство производным + rate-limit.

### 3.0. Жёсткие отказы (проверяются ДО скоринга)

> ⚠️ **Исправление аудита.** Раньше replay был слагаемым скоринга в 15 баллов. Но
> пройденный heart gate даёт пол в 60 баллов, а порог отказа — 50. Из-за этого
> **обнаруженный replay набирал 85 и принимался как VALID**, а санкция из §11
> («REJECTED с replay-hash → бан Dojo 7 дней») была недостижима в принципе.
> Дублирование записи — это факт, а не вероятностный сигнал, поэтому оно вынесено
> из скоринга в жёсткие отказы.

Следующие условия отклоняют запись **немедленно**, минуя скоринг:

| Условие | Вердикт | Действие |
|---|---|---|
| `heartGate` не пройден | REJECTED | мягкое сообщение, карта не создаётся |
| Нет допустимого platform-attestation verdict или подпись payload неверна | PENDING/REJECTED | временный сбой → локальная очередь; постоянный/скомпрометированный verdict → отказ |
| `nonce` неизвестен, истёк или уже использован | REJECTED | лог `replay_nonce_invalid` |
| `replay_hash` уже встречался | REJECTED | лог `replay_detected` → санкция §11 |
| Превышен `DOJO_DAILY_LIMIT` или интервал < 1 мин | REJECTED | сообщение «лимит на сегодня» |

Только запись, прошедшая все четыре, попадает в скоринг §3.1.

### 3.1. Античит-score (для оттенков между «валидно» и «подозрительно»)

Скоринг **не решает, принять ли запись** — это уже сделано в §3.0. Он решает,
пометить ли её для ревью.

```
score = 60                                     // база: heart gate пройден (иначе мы сюда не дошли)
if client_entropy_in_range:        score += 20  // клиент считает, сервер проверяет диапазон
if type_distribution_normal:       score += 20  // §3.5, вероятностный аудит типа удара

verdict:
  >= 80 → VALID       (принять)
  50-79 → SUSPECT     (принять, пометить в anticheat_events; после N пометок → review)
```

Отдельного значения `< 50` здесь нет: всё, что подлежало отказу, отсеяно в §3.0.

### 3.2. Heart Gate (жёсткий шлюз, см. §3.0)
Подробно — `docs/02-mechanics/MECHANIC_HEART_GATE.md`. Кратко:
```
heartGate = (present >= 0.80) AND (mean >= baseline+8) AND (mean >= 55) AND (confidence >= 0.85)
```
На официальном некомпрометированном клиенте пульс — сильный сигнал контакта с телом,
поэтому он используется как шлюз. На root/jailbreak или модифицированном клиенте
значения могут быть подменены; такие клиенты отсекаются attestation policy §2.1.

> ⚠️ **Что именно доказывает пульс.** Он подтверждает, что часы надеты на живом теле
> в состоянии нагрузки. Он **не** доказывает, что был нанесён удар: прыжки на месте
> с тряской запястья проходят гейт. Это принятое ограничение — см. §3.7.

> ⚠️ **Прохождение гейта — обязательное условие создания карты.** Режима
> «запись без пульса даёт карту низкой редкости» не существует (см.
> `MECHANIC_HEART_GATE.md` §7.1). Любая деградация, которая обходит гейт,
> означает, что Dojo недоступен, а не что карта хуже.

### 3.3. Replay-detection — серверный, жёсткий отказ (§3.0)
- **Сервер выдаёт одноразовый nonce** в `/dojo/preflight` (клиент НЕ генерирует — исправление аудита P3).
- Nonce имеет TTL 5 минут, валидируется один раз, инвалидируется после использования.
- Replay-hash = `SHA-256(nonce || evidence_schema_version || metrics_canonical_json || heart_evidence_canonical_json || feature_summary_canonical_json)`.
- Сервер хранит hash в Redis с TTL 90 дней. Повтор того же hash → REJECTED + флаг.
- Что НЕ передаётся: сырой сигнал, FFT-бины, спектр. Только каноникализированные производные метрики.

### 3.3a. Attestation и подпись Dojo payload

- `/dojo/preflight` возвращает `nonce`, `expiresAt`, `evidenceSchemaVersion` и случайный `challenge` для platform attestation.
- Wear OS MVP использует Play Integrity Standard API. Базовая server policy
  требует `PLAY_RECOGNIZED`, `LICENSED`, `MEETS_DEVICE_INTEGRITY`, совпадающие
  package/versionCode/signing certificate и свежий timestamp. Gate 1/3 может
  усилить policy до `MEETS_STRONG_INTEGRITY`, но не ослабить базовый набор.
- iOS/watchOS в Beta использует App Attest, а при документированном отсутствии поддержки на конкретном target — DeviceCheck с более низким trust tier.
- При регистрации устройства клиент создаёт аппаратно защищаемый ключ, если платформа это позволяет. Сервер хранит public key и привязку к account/device.
- `/dojo/submit` подписывает канонический payload: `nonce`, schema version, timestamps, metrics, heart evidence, feature summary, classifier version и app build.
- Play Integrity `requestHash` привязывает verdict к тому же submit и challenge:
  `base64url(SHA-256("gochya-dojo-play-integrity-v1" || 0x00 || challenge || 0x00 || canonical_payload))`
  без `=` padding. `appBuild` равен десятичному Play `versionCode`.
- Backend объединяет параллельное декодирование одинакового Standard token и
  хранит проверенный результат две минуты по SHA-256 от token + `requestHash`.
  Сам encrypted token и временные ошибки в локальный кэш не записываются.
- Недоступность attestation-сервиса не выдаёт карту: запись хранится локально как `PENDING` до истечения nonce либо пользователь получает безопасный retry.
- Attestation не превращает client features в доказанный raw signal. Она лишь повышает уверенность, что признаки вычислил разрешённый build в приемлемом окружении.

### 3.3b. Privacy-safe feature summary

Вместо одного `client_entropy` клиент передаёт фиксированный schema-versioned summary без временного ряда:

```text
sample_count_accel, sample_count_gyro, sample_count_hr
duration_ms, monotonic_start_ms, monotonic_end_ms
accel_peak, accel_rms, gyro_peak, gyro_rms
entropy_16bin, zero_crossing_count
hr_present_ratio, hr_mean, hr_delta, contact_confidence
classifier_id, classifier_version, technique_type, confidence
```

Сервер проверяет внутреннюю согласованность: длительность и sample counts, физические
диапазоны, монотонность времени, согласованность summary с итоговыми metrics и
разрешённую версию классификатора. Summary не позволяет восстановить исходный жест
и не заменяет raw-signal validation; его задача — сделать дешёвую произвольную
подмену сложнее и наблюдаемее.

### 3.4. Клиентская энтропия (20 баллов в скоринге)
- Клиент считает **Shannon entropy** на magnitude ускорения (`|a| = sqrt(ax²+ay²+az²)`) по окну записи.
```
H = -Σ p(x) · log2(p(x))     // по гистограмме из 16 бинов, нормированной на [0, max_accel]
```
- Передаёт на сервер **одно число** `client_entropy` (float).
- Сервер проверяет диапазон: `2.5 <= client_entropy <= 4.0` для валидной записи.
  - `< 2.5` → подозрение на циклический буфер / повторяющуюся тряску.
  - `> 4.0` → невозможное значение для 16 бинов, запись отклоняется как
    несогласованная (`log2(16) = 4`).
- Это слабая эвристика, но в сочетании с heart gate отсекает большинство дешёвых читов.

### 3.5. Вероятностный аудит типа удара (post-factum, не блокирует)
- **Решение аудита S2:** тип удара (`technique_type`) — доверенный клиентский ввод (edge-ML классификация). Сервер не может его верифицировать без сырого сигнала.
- Вместо жёсткой валидации — **вероятностный аудит**: сервер ведёт распределение типов за последние 30 записей игрока.
```
type_distribution[TechniqueType] -> float  // нормализованная частота

anomaly_check:
  if any type has frequency > 0.80 over last 30 records:
      flag SUSPECT (но не блокировать — возможно, игрок просто тренирует один удар)
  if type frequency matches random uniform (>0.15 each) AND quality всегда высокий:
      flag SUSPECT (возможно, подмена типа для матчмейкинг-абуза)
```
- Действие: накопление 5+ SUSPECT-флагов → manual review командой.

### 3.6. Rate-limit — жёсткий отказ (§3.0)
- Не больше `DOJO_DAILY_LIMIT = 10` записей/день.
- Не больше 1 записи в минуту (анти-AFK).
- Превышение — отказ с понятным сообщением, а не снижение балла.

### 3.7. Чего НЕТ в античите (намеренно)
- ❌ Серверной спектральной валидации (требует сырой сигнал).
- ❌ Серверной гироскопической валидации (требует сырой сигнал).
- ❌ Серверной проверки «формы удара» (требует сырой сигнал).
- ❌ Серверной верификации типа удара (требует сырой сигнал).
- ❌ Криптографической подписи Health-данных (HealthKit/Samsung Health не предоставляют подписи — см. §5.5).

**Обоснование:** privacy-first — архитектурный принцип проекта (см. `00-MASTER-PROMPT.md §2.4`). Античит не доказывает физический удар: он сочетает attestation, heart gate, согласованность производных признаков, лимиты и post-factum анализ. Глубокая защита от целенаправленных читеров без передачи raw signal недостижима; остаточный риск принимается и ограничивается экономическими caps и trust tiers.

## 4. PvP — ВАЛИДАЦИЯ БОЯ

### 4.1. Серверный расчёт
- Клиент отправляет только **ID выбранных карт** + loadout (из инвентаря, который тоже серверный).
- Сервер:
  1. Загружает питомца и инвентарь из БД.
  2. Проверяет, что выбранные карты действительно есть у игрока.
  3. Считает бой через `core::simulate_combat(match, seed)`.
  4. Сохраняет `MatchResult` + раунды для replay.
  5. Начисляет награды, обновляет ELO.

### 4.2. Подмена loadout
- Нельзя: loadout проверяется против серверного инвентаря.
- Питомец должен быть `is_active` и принадлежать игроку.

### 4.3. Win-trading detection
- Анализ паттернов: одни и те же пары играют много игр с предсказуемым исходом.
- Подозрительные пары → временный бан матчмейкинга между ними → review.

### 4.4. Smurfing / boost
- ELO-матчмейкинг с K-factor больше для новых аккаунтов.
- IP/device fingerprint: один device → один активный аккаунт в ранговом режиме.

## 5. СИМБИОЗ — ВАЛИДАЦИЯ АКТИВНОСТИ

### 5.1. Дедупликация устройств
- Дедупликация выполняется по source record provenance и overlap, а не грубым правилом «часы побеждают весь день».
- Нормативный алгоритм — `docs/03-architecture/HEALTH_DATA_CONTRACT.md`.

### 5.2. Валидация типов активности
- Samsung Health / HealthKit сами фильтруют «в машине» vs «ходьба».
- Сервер игнорирует шаги, если тип активности = `IN_VEHICLE`.

### 5.3. Soft cap
- 50 000 шагов → capped до 18 000 (для цели). Vitality capped 150.

### 5.4. Аномалии
- Резкий скачок с 3000 до 40 000 шагов → флаг, но не блокировка.
- Сон 12 часов → флаг.
- Стрик 365 дней → флаг на ревью (возможно, бот).

### 5.5. Source metadata (НЕ подпись)
> ⚠️ **Исправление аудита T5:** прежнее утверждение «HealthKit/Samsung Health предоставляют подписанные данные» — **неверно**. Оба API предоставляют только metadata об источнике (`HKSource` / эквивалент Samsung), которую **можно подделать на jailbreak/root устройстве**. Криптографической подписи агрегатов для сторонних приложений нет.

- Сервер хранит `source_metadata` каждого snapshot (строку: `healthkit://iPhone` / `samsung_health://watch` / и т.д.).
- Это используется только для дедупликации и приоритизации источников (часы > телефон), **не** как античит-доказательство.
- Реальная защита от подделки health-данных: дедупликация, soft cap, anomaly detection (см. §5.1–5.3).

## 6. ЭКОНОМИКА — DOUBLE-ENTRY LEDGER

### 6.1. Принцип
- Каждое изменение валюты — **транзакция с двумя сторонами** (debit/credit).
- Никогда не делаем `wallet.koins += X` напрямую. Только через `ledger.apply(transaction)`.

```
transactions:
    tx_id | player_id | currency | amount | reason | ref_id | timestamp
```

### 6.2. Баланс всегда сходится
- `sum(transactions for player, currency) == wallet[currency]`.
- Periodic consistency check (cron-job).

### 6.3. Anomaly detection
- Резкий рост валюты без IAP → флаг.
- Отрицательный баланс → rollback + бан.

---

## 7. IAP-ВАЛИДАЦИЯ

- Каждая покупка валидируется сервером через App Store Server API / Google Play Developer API / Galaxy Store IAP.
- Idempotency: `transactionId` уникален, повторная валидация = no-op.
- Подписки: слушаем webhooks (App Store Server Notifications V2, RTDN, Galaxy webhooks).
- Refund → отзыв награды (transaction reversal в ledger).

---

## 8. АВТОРИЗАЦИЯ И СЕССИИ

- JWT с коротким TTL (15 мин) + refresh-token (30 дней).
- Refresh-rotation: каждый refresh инвалидирует предыдущий; абсолютный lifetime
  token family — 90 дней.
- В PostgreSQL хранится только 32-byte SHA-256 refresh-токена. Повтор уже
  отозванного токена помечается как reuse и атомарно отзывает всю token family.
- Logout не раскрывает, существовал ли переданный токен, и отзывает всю family.
- Google login принимает только подписанный ID token с разрешённым OAuth client
  ID, Google issuer, актуальным сроком и стабильным `sub`. Переданный клиентом
  Google user ID или email не принимается как доказательство личности.
- Device binding: опциональная привязка аккаунта к device fingerprint (для чувствительных действий).
- 2FA — опционально для аккаунтов с IAP-историей.

## 9. ТРАНСПОРТ И СЕКРЕТЫ

- **TLS 1.3** обязателен. Certificate pinning в клиенте.
- **Подпись payload:** устройство использует зарегистрированный attested key; симметричный секрет, извлекаемый из клиента, не считается границей доверия.
- Секреты — в Vault/KMS, не в коде/репозитории.
- SAST в CI: проверка на хардкод ключей, небезопасные паттерны.

## 10. ПРИВАТНОСТЬ (COMPLIANCE)

| Ресурс | Что хранится | consent |
|---|---|---|
| Health-данные (агрегаты) | дневные снапшоты (шаги, сон, калории) | явный consent, можно отозвать |
| Сырой сигнал сенсоров | **не хранится, не покидает device** | — |
| Пульс (производные) | `HR_present/mean/delta/confidence` (4 числа) | явный consent |
| Профиль игрока | username, auth_subject, timezone | стандартный ToS |
| Дети (<13) | нет сбора без parental consent (COPPA) | COPPA/GDPR-K режим |

- GDPR: право на экспорт/удаление данных.
- Удаление аккаунта → каскадное удаление всех данных за 30 дней.

## 11. ДЕЙСТВИЯ ПО НАРУШЕНИЯМ

| Сигнал | Авто-действие |
|---|---|
| 1 SUSPECT-запись | ничего (лог) |
| 5 SUSPECT-записей/неделю | temporary Dojo ban 24ч + warning |
| REJECTED-запись с replay-hash | ban Dojo 7 дней |
| Win-trading | 7-дневный матч-бан + review |
| Currency anomaly | rollback + 30-дневный бан |
| IAP-fraud | permanent ban + refund-chain |
| Bot-pattern (device fingerprint) | shadow-ban + review |
