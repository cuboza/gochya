# АНТИЧИТ И БЕЗОПАСНОСТЬ

> Многослойная защита. Главный принцип: **сервер — авторитет**, клиент — тонкий. Подробности по механикам — в `docs/02-mechanics/`.
>
> **Архитектурное решение (аудит S1+S2):** privacy-first финализирован. Античит работает **только** на производных метриках, покидающих устройство; сырой сигнал сенсоров **никогда** не передаётся. Это физически исключает «серверную спектральную/гироскопическую валидацию» — эти слои убраны (см. §3). Вместо них: heart gate + replay-detection + клиентская энтропия + вероятностный аудит типа удара. Тип удара — доверенный клиентский ввод (см. §3.5).

## 3. DOJО — ВАЛИДАЦИЯ ЗАПИСИ УДАРА

> ⚠️ **Переработано в аудите (S1).** Прежние §3.3 «спектральная подпись на сервере» и §3.4 «гироскопическая сигнатура на сервере» **удалены как физически невозможные**: валидация формы сигнала требует передачи самого сигнала, что нарушает privacy-first принцип. Античит сведён к трём покидающим устройство производным + rate-limit.

### 3.1. Античит-score (упрощённый, privacy-safe)
```
score = 0
if heartGate passed:                     score += 60   // главный и самый надёжный слой
if replay_check_ok (server-side nonce):  score += 15
if client_entropy_in_range:              score += 15   // клиент считает, сервер проверяет диапазон
if rate_limit_ok:                        score += 10

verdict:
  >= 75 → VALID       (принять)
  50-74 → SUSPECT     (принять, пометить в anticheat_events; после N пометок → review)
  < 50  → REJECTED    (отклонить, мягкое сообщение)
```

### 3.2. Heart Gate (главный слой, 60 баллов)
Подробно — `docs/02-mechanics/MECHANIC_HEART_GATE.md`. Кратко:
```
heartGate = (present >= 0.80) AND (mean >= baseline+8) AND (mean >= 55) AND (confidence >= 0.85)
```
Пульс — единственный сигнал, который нельзя подделать без часов на живом теле.

### 3.3. Replay-detection (15 баллов) — серверный
- **Сервер выдаёт одноразовый nonce** в `/dojo/preflight` (клиент НЕ генерирует — исправление аудита P3).
- Nonce имеет TTL 5 минут, валидируется один раз, инвалидируется после использования.
- Replay-hash = `SHA-256(nonce || metrics_canonical_json || heart_evidence_canonical_json)`.
- Сервер хранит hash в Redis с TTL 90 дней. Повтор того же hash → REJECTED + флаг.
- Что НЕ передаётся: сырой сигнал, FFT-бины, спектр. Только каноникализированные производные метрики.

### 3.4. Клиентская энтропия (15 баллов)
- Клиент считает **Shannon entropy** на magnitude ускорения (`|a| = sqrt(ax²+ay²+az²)`) по окну записи.
```
H = -Σ p(x) · log2(p(x))     // по гистограмме из 16 бинов, нормированной на [0, max_accel]
```
- Передаёт на сервер **одно число** `client_entropy` (float).
- Сервер проверяет диапазон: `2.5 <= client_entropy <= 6.0` для валидной записи.
  - `< 2.5` → подозрение на циклический буфер / повторяющуюся тряску.
  - `> 6.0` → подозрение на синтетический шум (равномерное распределение).
- Это слабая эвристика, но в сочетании с heart gate отсекает большинство дешёвых читов.

### 3.5. Вероятностный аудит типа удара (post-factum, не блокирует)
- **Решение аудита S2:** тип удара (`technique_type`) — доверенный клиентский ввод (edge-ML классификация). Сервер не может его верифицировать без сырого сигнала.
- Вместо жёсткой валидации — **вероятностный аудит**: сервер ведёт распределение типов за последние 30 записей игрока.
```
type_distribution[TechniqueType] -> float  // нормализованная частота

anomaly_check:
  if any type has frequency > 0.80 over last 30 records:
      flag SUSPECT (но не блокировать — возможно, игрок просто тренирует один удар)
  if type frequency matches random uniform (>0.15 each) AND quality всегда высокий:
      flag SUSPECT (возможно, подмена типа для матчмейкинг-абуза)
```
- Действие: накопление 5+ SUSPECT-флагов → manual review командой.

### 3.6. Rate-limit (10 баллов)
- Не больше `DOJO_DAILY_LIMIT = 10` записей/день.
- Не больше 1 записи в минуту (анти-AFK).

### 3.7. Чего НЕТ в античите (намеренно)
- ❌ Серверной спектральной валидации (требует сырой сигнал).
- ❌ Серверной гироскопической валидации (требует сырой сигнал).
- ❌ Серверной проверки «формы удара» (требует сырой сигнал).
- ❌ Серверной верификации типа удара (требует сырой сигнал).
- ❌ Криптографической подписи Health-данных (HealthKit/Samsung Health не предоставляют подписи — см. §5.5).

**Обоснование:** privacy-first — архитектурный принцип проекта (см. `00-MASTER-PROMPT.md §2.4`). Античит основан на том, что **подделать пульс на живом теле нельзя**, а остальные слои — вспомогательные для отсечения дешёвых автоматизированных читов. Глубокая защита от целенаправленных читеров достигается через экономические механизмы (cap качества, матчмейкинг по effective power) и ручной review паттернов.

## 4. PvP — ВАЛИДАЦИЯ БОЯ

### 4.1. Серверный расчёт
- Клиент отправляет только **ID выбранных карт** + loadout (из инвентаря, который тоже серверный).
- Сервер:
  1. Загружает питомца и инвентарь из БД.
  2. Проверяет, что выбранные карты действительно есть у игрока.
  3. Считает бой через `core::simulate_combat(match, seed)`.
  4. Сохраняет `MatchResult` + раунды для replay.
  5. Начисляет награды, обновляет ELO.

### 4.2. Подмена loadout
- Нельзя: loadout проверяется против серверного инвентаря.
- Питомец должен быть `is_active` и принадлежать игроку.

### 4.3. Win-trading detection
- Анализ паттернов: одни и те же пары играют много игр с предсказуемым исходом.
- Подозрительные пары → временный бан матчмейкинга между ними → review.

### 4.4. Smurfing / boost
- ELO-матчмейкинг с K-factor больше для новых аккаунтов.
- IP/device fingerprint: один device → один активный аккаунт в ранговом режиме.

## 5. СИМБИОЗ — ВАЛИДАЦИЯ АКТИВНОСТИ

### 5.1. Дедупликация устройств
- Если часы и телефон шлют данные за один день → приоритет **часам** (точнее).
- Если несколько часов → приоритет последнему активному.

### 5.2. Валидация типов активности
- Samsung Health / HealthKit сами фильтруют «в машине» vs «ходьба».
- Сервер игнорирует шаги, если тип активности = `IN_VEHICLE`.

### 5.3. Soft cap
- 50 000 шагов → capped до 18 000 (для цели). Vitality capped 150.

### 5.4. Аномалии
- Резкий скачок с 3000 до 40 000 шагов → флаг, но не блокировка.
- Сон 12 часов → флаг.
- Стрик 365 дней → флаг на ревью (возможно, бот).

### 5.5. Source metadata (НЕ подпись)
> ⚠️ **Исправление аудита T5:** прежнее утверждение «HealthKit/Samsung Health предоставляют подписанные данные» — **неверно**. Оба API предоставляют только metadata об источнике (`HKSource` / эквивалент Samsung), которую **можно подделать на jailbreak/root устройстве**. Криптографической подписи агрегатов для сторонних приложений нет.

- Сервер хранит `source_metadata` каждого snapshot (строку: `healthkit://iPhone` / `samsung_health://watch` / и т.д.).
- Это используется только для дедупликации и приоритизации источников (часы > телефон), **не** как античит-доказательство.
- Реальная защита от подделки health-данных: дедупликация, soft cap, anomaly detection (см. §5.1–5.3).

## 6. ЭКОНОМИКА — DOUBLE-ENTRY LEDGER

### 6.1. Принцип
- Каждое изменение валюты — **транзакция с двумя сторонами** (debit/credit).
- Никогда не делаем `wallet.koins += X` напрямую. Только через `ledger.apply(transaction)`.

```
transactions:
    tx_id | player_id | currency | amount | reason | ref_id | timestamp
```

### 6.2. Баланс всегда сходится
- `sum(transactions for player, currency) == wallet[currency]`.
- Periodic consistency check (cron-job).

### 6.3. Anomaly detection
- Резкий рост валюты без IAP → флаг.
- Отрицательный баланс → rollback + бан.

---

## 7. IAP-ВАЛИДАЦИЯ

- Каждая покупка валидируется сервером через App Store Server API / Google Play Developer API / Galaxy Store IAP.
- Idempotency: `transactionId` уникален, повторная валидация = no-op.
- Подписки: слушаем webhooks (App Store Server Notifications V2, RTDN, Galaxy webhooks).
- Refund → отзыв награды (transaction reversal в ledger).

---

## 8. АВТОРИЗАЦИЯ И СЕССИИ

- JWT с коротким TTL (15 мин) + refresh-token (30 дней).
- Refresh-rotation: каждый refresh инвалиддирует предыдущий.
- Device binding: опциональная привязка аккаунта к device fingerprint (для чувствительных действий).
- 2FA — опционально для аккаунтов с IAP-историей.

---

## 9. ТРАНСПОРТ И СЕКРЕТЫ

- **TLS 1.3** обязателен. Certificate pinning в клиенте.
- **HMAC payload:** каждое устройство имеет уникальный `device_key`, payload подписан.
- Секреты — в Vault/KMS, не в коде/репозитории.
- SAST в CI: проверка на хардкод ключей, небезопасные паттерны.

## 10. ПРИВАТНОСТЬ (COMPLIANCE)

| Ресурс | Что хранится | consent |
|---|---|---|
| Health-данные (агрегаты) | дневные снапшоты (шаги, сон, калории) | явный consent, можно отозвать |
| Сырой сигнал сенсоров | **не хранится, не покидает device** | — |
| Пульс (производные) | `HR_present/mean/delta/confidence` (4 числа) | явный consent |
| Профиль игрока | username, auth_subject, timezone | стандартный ToS |
| Дети (<13) | нет сбора без parental consent (COPPA) | COPPA/GDPR-K режим |

- GDPR: право на экспорт/удаление данных.
- Удаление аккаунта → каскадное удаление всех данных за 30 дней.

## 11. ДЕЙСТВИЯ ПО НАРУШЕНИЯМ

| Сигнал | Авто-действие |
|---|---|
| 1 SUSPECT-запись | ничего (лог) |
| 5 SUSPECT-записей/неделю | temporary Dojo ban 24ч + warning |
| REJECTED-запись с replay-hash | ban Dojo 7 дней |
| Win-trading | 7-дневный матч-бан + review |
| Currency anomaly | rollback + 30-дневный бан |
| IAP-fraud | permanent ban + refund-chain |
| Bot-pattern (device fingerprint) | shadow-ban + review |
