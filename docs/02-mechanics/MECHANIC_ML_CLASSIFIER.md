# МЕХАНИКА: ML-классификатор ударов (Dojo)

> **Аудит C2 (блокер MVP):** спецификация классификатора отсутствовала — ML-инженер не мог начать работу. Этот файл заполняет пробел: алгоритм, сигнал, шаблоны, метрики, план сбора данных.

---

## 1. ЦЕЛЬ

Классифицировать тип удара из 6-секундной записи акселерометра+гироскопа. Тип определяет `TechniqueType` → влияет на `element`, `baseDamage`, `rarity`, `effect` карты (см. `MECHANIC_COMBAT_RECORDING.md`).

> ⚠️ **Архитектурный контекст (audit S2):** классификация происходит **на клиенте** (edge ML). Тип удара — доверенный клиентский ввод; сервер не может его верифицировать без сырого сигнала (нарушит privacy). Защита — вероятностный аудит распределения типов (`ANTICHEAT.md §3.5`).

## 2. MVP — DTW ПО ШАБЛОНАМ

### 2.1. Почему DTW, а не нейросеть (для MVP)
- **Объяснимость:** понятно, почему «хук» — это «хук» (визуализация пути выравнивания).
- **Мало данных:** не нужен датасет из тысяч записей для обучения, достаточно ~50 эталонов на тип.
- **Детерминизм:** одинаковые входы → одинаковый класс (важно для паритета платформ).
- **Малый размер:** 5 шаблонов × ~600 сэмплов × 2 ряда = ~60 КБ (помещается в watchOS bundle).
- **Быстрый имплемент:** нет зависимости от Core ML / TFLite.

Фаза 2: замена на нейросеть (Core ML / TFLite / ONNX), обученную на собранном датасете.

### 2.2. Сигнал
- **2 ряда:** `accel_magnitude` и `gyro_magnitude`.
  ```
  accel_mag[i] = sqrt(ax[i]² + ay[i]² + az[i]²)
  gyro_mag[i]  = sqrt(gx[i]² + gy[i]² + gz[i]²)
  ```
- **Частота сэмплирования:** 50 Гц (целевая; `SENSOR_DELAY_GAME` на Android, `1/50` на CoreMotion).
- **Окно:** 6 секунд → ~300 сэмплов × 2 ряда = ~600 значений.

### 2.3. Препроцессинг
1. **Detrend:** вычесть скользящее среднее (окно 0.5 сек) — убрать гравитационную компоненту и дрейф.
2. **Normalise:** разделить на `max(accel_mag)` в окне — привести к диапазону [0, 1].
3. **Trim silence:** обрезать начальные/конечные сэмплы, где `accel_mag < 0.1 · peak` (покой до/после удара).

### 2.4. Шаблоны (5 типов для MVP)
| Тип | Файл | Источник | Описание |
|---|---|---|---|
| Jab | `templates/jab.json` | запись боксёра | прямой короткий удар, пик ~30–50 м/с² |
| Hook | `templates/hook.json` | запись боксёра | боковой удар, выраженное вращение в gyro |
| Uppercut | `templates/uppercut.json` | запись боксёра | удар снизу вверх, пик в вертикальной компоненте |
| Kick | `templates/kick.json` | запись | удар ногой, большая амплитуда, длиннее |
| Block | `templates/block.json` | запись | защитное движение, низкий пик, широкое |

Каждый шаблон — **усреднённый** сигнал из 10–15 качественных записей одного бойца, тот же препроцессинг (detrend + normalise + trim).

### 2.5. Алгоритм DTW
- **Метрика:** Euclidean distance между 2-мерными точками `(accel_mag, gyro_mag)`.
- **Sakoe-Chiba band:** ширина `w = 0.3 · window_length` — ограничивает warp, ускоряет вычисление и предотвращает «сильные» искажения.
- **Реализация:** стандартная DTW с матрицей накопления `D[i][j]`, `O(n·m)` по времени и памяти (~300×300 = 90K float = 360 КБ — помещается в RAM часов).

```
for each template t in templates:
    dtw_dist[t] = DTW(input_signal, t, band=w)
best_match = argmin(dtw_dist)
```

### 2.6. Извлечение метрик
- **`technique_type`** = `best_match` (argmin DTW distance).
- **`precision`** = `clamp(1 - dtw_dist[best_match] / NORMALISATION_CONST, 0, 1)`.
  - `NORMALISATION_CONST` — калибруется на датасете так, чтобы 95-й перцентиль расстояний у «хороших» записей давал `precision ≈ 0.9`, а у «плохих» — `≈ 0.3`.
  - Начальное значение: `NORMALISATION_CONST = 5.0` (уточнить после сбора данных).
- **`peak_accel`** = `max(accel_mag) · G` (м/с²), где `G = 9.81` (нормализация платформенного диапазона).
- **`exec_time`** = индекс пика − индекс старта (в секундах).

### 2.7. Сегментация комбо (несколько ударов в окне)
- **Peak detection:** найти все локальные максимумы `accel_mag`, превышающие `0.3 · peak_accel`, с минимальным интервалом 0.2 сек.
- **`combo_len`** = число обнаруженных пиков (кап 5).
- **`rhythm_score`** = `1 - normalised_variance(intervals_between_peaks)`.
  - Равномерные интервалы → `rhythm_score ≈ 1` (ритмичный комбо).
  - Хаотичные интервалы → `rhythm_score ≈ 0`.

## 3. ПЛАН СБОРА ДАННЫХЕТСА

> ⚠️ Это **отдельная задача** (не в Core-разработке). ML-инженер + 5 бойцов-добровольцев.

| Параметр | Значение |
|---|---|
| Бойцов | 5 (разного уровня: 2 новичка, 2 среднего, 1 опытный) |
| Типов ударов | 5 (Jab/Hook/Uppercut/Kick/Block) |
| Повторов на тип | 50 |
| Сессий на бойца | 5 × 50 = 250 записей |
| **Итого записей** | **1250** |
| Устройства | Galaxy Watch 6 + Apple Watch S9 (оба для паритета) |
| Разметка | ручная: тип + качество (good/medium/bad) + отбраковка артефактов |
| Consent | явный письменный + GDPR-совместимое хранение |

- Из 1250 записей: ~1000 идут в шаблоны/калибровку, ~250 — holdout для валидации.
- Эталоны-шаблоны: top-15 записей на тип по качеству → усреднение.

## 4. ПАРИТЕТ ПЛАТФОРМ

> **Аудит R3/B4:** разное качество классификации на watchOS и Wear OS ломает «детерминизм» на уровне ввода.

### Принцип
- **Один алгоритм** (DTW), **одни шаблоны** (5 JSON-файлов), **один препроцессинг**.
- Реализация — на Kotlin (Wear OS) и Swift (watchOS), идентичная логика.
- **Golden-тесты:** для 50 эталонных сигналов зафиксировать ожидаемые `(technique_type, precision)` и проверять на обеих платформах. Расхождение > 0.05 в precision → баг.

### Будущее (фаза 2): единый ONNX
- Обучить нейросеть на Python (PyTorch).
- Экспорт в **ONNX** как единственный источник.
- watchOS: ONNX → Core ML (`coremltools`).
- Wear OS: ONNX → ONNX Runtime Android или TFLite (`onnx-tf` → TFLite).
- Паритет гарантируется одним исходником.

## 6. ПЕРЕХОД НА НЕЙРОСЕТЬ (фаза 2)

Критерии перехода:
- Датасет ≥ 5000 записей (после soft launch).
- DTW-точность < 85% на holdout (измерять).
- Жалобы игроков на неправильную классификацию > 5%.

Архитектура модели (планируемая):
- 1D-CNN по `(accel_mag, gyro_mag)` рядам.
- Вход: `[2, 300]`, выход: softmax по 5 + regression для `precision`.
- Размер: <500 КБ (quantised int8).
- Core ML + TFLite из единого ONNX.
